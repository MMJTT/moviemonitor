# TicketWatch 轻量私有服务器版设计规格

日期：2026-08-17

状态：交互设计已确认，待书面规格审阅

对应分支：`feature/ticket-monitor`

## 1. 背景与决策

TicketWatch 当前已经形成可在本机使用的单用户 MVP 闭环：用户可以创建多条猫眼监控任务，系统按“城市、电影、观影日期、影院”精确检查开票状态，并通过 Agent Mail 从 `mijiatong@agent.qq.com` 向 `850634546@qq.com` 发送提醒。

下一阶段先把现有 MVP 搬到阿里云服务器长期运行，不立即建设公网、多用户或 OpenClaw 能力。已确认的关键决策如下：

- 服务器为阿里云 Linux 4，2 核 CPU、1.8 GiB 内存、6 GiB Swap、40 GB 系统盘；
- 用户量很少，不升级服务器配置；
- 第一阶段只有所有者本人使用；
- Web 页面不向公网开放，通过 SSH 隧道访问；
- 阿里云安全组只开放 SSH，暂不使用域名、HTTPS 或 ICP 备案；
- 永久数据从 SQLite 迁移至 PostgreSQL；
- Redis 只承担唤醒和短期互斥，不作为任务或通知的永久来源；
- 使用独立轻量 Worker，不引入 Celery、Celery Beat 或多个专用 Worker；
- 保留 Agent Mail，不恢复用户 SMTP；
- OpenClaw、LLM、用户系统和其他票务平台推迟到后续阶段。

## 2. 目标

本阶段交付一个可长期运行、可恢复、可备份的私有服务器版本，满足以下目标：

1. 所有者通过 SSH 隧道使用现有 Web 界面；
2. Web 服务停止或重启时，监控 Worker 仍可独立运行；
3. 服务器或容器重启后，监控任务能从 PostgreSQL 自动恢复；
4. Redis 丢失或重启不造成任务、检查记录或通知记录丢失；
5. 多条监控任务可以独立调度；
6. 三级检查频率可以在网页中修改，但任何间隔不得低于 60 秒；
7. 真实猫眼开票能够触发唯一一次 Agent Mail 提醒；
8. 数据库有经过恢复演练的备份，而不仅是生成备份文件。

## 3. 非目标

本阶段明确不实现：

- 公网网站、域名接入、Nginx、HTTPS 或 ICP 备案；
- 注册、登录、邀请、用户隔离和管理员后台；
- 用户自定义 SMTP 或收件邮箱；
- OpenClaw、LLM API、自然语言任务创建；
- 自动发现全部电影或影院；
- 大麦或其他平台适配；
- 自动选座、下单、付款或验证码绕过；
- 高并发和水平扩容；
- PostgreSQL 或 Redis 公网访问。

## 4. 总体架构

服务器使用 Docker Compose 管理四个服务：

| 服务 | 职责 | 永久状态 | 公网端口 |
|---|---|---|---|
| `web` | Django 页面、任务 CRUD、设置和查看记录 | 否 | 无；只映射到宿主机 `127.0.0.1:8000` |
| `worker` | 到期任务检查、过期处理、通知发送与重试 | 否 | 无 |
| `postgres` | 任务、设置、检查记录和通知记录 | 是 | 无 |
| `redis` | Worker 唤醒、短期互斥和轻量协调 | 否 | 无 |

访问链路为：

```text
Mac 浏览器
  -> 127.0.0.1:18000
  -> SSH 隧道
  -> 服务器 127.0.0.1:8000
  -> Django Web
  -> PostgreSQL / Redis

Worker
  -> PostgreSQL 领取到期任务
  -> 猫眼真实页面
  -> PostgreSQL 写入检查与通知状态
  -> Agent Mail CLI 发送提醒
```

Web 只处理请求，不启动进程内调度线程。Worker 是唯一执行后台工作的常驻进程，并发固定为 1。

## 5. 服务器目录与持久化

统一部署目录：

```text
/opt/ticketwatch/
├── app/                 # Git 仓库工作目录
├── data/
│   ├── postgres/        # PostgreSQL 数据目录
│   ├── redis/           # 可选 Redis 持久化目录
│   ├── agently/         # Agent Mail CLI 工作区及授权状态
│   └── backups/         # PostgreSQL 压缩备份
├── logs/                # 有上限的宿主机运维日志
└── .env                 # 服务器专用环境变量，权限 0600
```

PostgreSQL 和 Agent Mail 授权目录必须使用持久化卷。Redis 数据可以丢失；即使启用 AOF，也不能把 Redis 当作业务状态来源。

## 6. 数据设计与迁移

### 6.1 数据库切换

Django 通过环境变量读取 PostgreSQL 连接信息。本地测试仍可使用独立测试数据库，但服务器运行时禁止回退到 SQLite。生产启动检查发现数据库配置缺失时应直接失败，避免意外生成新的空 SQLite 数据库。

现有 `MonitorTask`、`CheckRun`、`Notification` 和 `AgentMailConfig` 数据应原样保留。迁移采用 Django 自然键或受控导出导入脚本，UUID 主键和时间戳不得重新生成。

`Notification.Type` 增加 `SYSTEM_ALERT`，用于任务因连续结构或配置错误进入异常状态时发送一次告警。`Notification.Status` 增加 `NEEDS_REVIEW`，用于邮件请求已经发出但进程未取得确定结果的情况。现有的 `(task, notification_type)` 唯一约束继续生效，因此每个任务的开票、到期和系统异常通知分别最多创建一条。

迁移顺序：

1. 停止本机调度器产生新写入；
2. 复制并校验 SQLite 备份；
3. 在空 PostgreSQL 中执行全部 Django migration；
4. 导入业务数据；
5. 比对各表数量、任务状态、通知唯一键和关键字段；
6. 在服务器上只读展示迁移结果；
7. 验证完成后再启动 Worker。

原 SQLite 文件至少保留到服务器验收和一次 PostgreSQL 恢复演练完成之后，不自动删除或覆盖。

### 6.2 三级检查频率

`AppSetting` 从单一 `poll_interval_seconds` 扩展为：

- `urgent_window_hours`：紧急区间边界，默认 48 小时；
- `near_window_days`：临近区间上界，默认 7 天；
- `urgent_interval_seconds`：48 小时内默认 60 秒；
- `near_interval_seconds`：2 至 7 天默认 300 秒；
- `far_interval_seconds`：7 天以上默认 900 秒。

所有间隔字段下限均为 60 秒。边界字段必须为正数，且 `near_window_days × 24` 必须大于 `urgent_window_hours`。修改设置后，所有“监控中”任务重新计算 `next_check_at`，但不得制造同一任务的并发检查。

区间按 `Asia/Shanghai` 计算，以目标日期当地时间 `00:00` 为边界：剩余时间小于等于 `urgent_window_hours` 时使用紧急间隔；否则，小于等于 `near_window_days` 时使用临近间隔；其余使用远期间隔。已经进入目标观影日但尚未到期的任务始终使用紧急间隔。设置保存后，监控中任务的下一次检查时间统一改为“保存时间 + 新区间间隔”。

旧的 `poll_interval_seconds` 在数据迁移时作为紧急区间间隔的初始值使用；完成一个兼容版本后再删除旧字段，避免不可逆的单步迁移。

### 6.3 Worker 领取租约

为 `MonitorTask` 增加短期领取信息：

- `claim_token`；
- `claim_expires_at`。

Worker 在短事务中使用 PostgreSQL 行锁选择最早到期任务并写入随机租约，然后在事务外执行网络请求。执行成功或失败后，以 `claim_token` 为条件提交结果并清理租约。Worker 崩溃后，过期租约可以重新领取。

第一阶段只有一个 Worker，但数据库租约能防止容器重启重叠或未来误启第二个 Worker时重复检查。通知唯一约束仍作为最终防重保障。

## 7. Worker 调度

### 7.1 主循环

Worker 每轮依次执行：

1. 更新心跳；
2. 处理到期任务；
3. 领取一条最早到期的监控任务；
4. 执行猫眼检查并记录 `CheckRun`；
5. 处理到期通知；
6. 若当前无工作，则等待 Redis 唤醒或短超时后重新扫描 PostgreSQL。

新建、修改、恢复任务或修改检查频率时，Web 尝试向 Redis 发送唤醒信号。Redis 写入失败不能使 Web 操作失败，因为 Worker 最迟会在下一次数据库扫描时发现变化。

Worker 并发固定为 1，不使用 Celery。Redis 互斥锁带有限 TTL；任务是否到期、是否完成和是否已经通知始终以 PostgreSQL 为准。

### 7.2 任务状态

保留现有状态并明确语义：

- `MONITORING`：等待或正在进行下一次检查；
- `PAUSED`：保留数据，不参与调度；
- `DETECTED`：已检测开票，等待通知最终结果；
- `COMPLETED`：开票邮件已成功发送；
- `EXPIRED`：目标观影日结束仍未开票；
- `CANCELLED`：用户主动终止；
- `ERROR`：连续多次发生需人工处理的异常。

任务达到终态后 `next_check_at` 必须为空。暂停、取消或完成任务时，未到期领取租约要安全失效，执行中的旧结果不得覆盖更新后的任务状态。

## 8. 猫眼检查与错误恢复

### 8.1 成功判定

保持现有严格条件：城市、电影 ID、日期和影院必须全部匹配；目标影院卡片必须出现可用的猫眼购票入口。HTTP 200 本身不代表业务成功。

首次检测到开票时：

1. 在同一数据库事务中记录 `detected_at` 和购票链接；
2. 创建唯一 `OPENING` 通知；
3. 停止该任务后续猫眼轮询；
4. 由通知调度继续发送，成功后任务进入 `COMPLETED`。

`Notification(task, notification_type)` 的数据库唯一约束保证同一任务的开票通知最多创建一条。

### 8.2 错误分类

- 网络超时、连接失败和猫眼临时 5xx：临时错误，自动退避；
- 猫眼限流、验证页或风控页：限流错误，延长重试；
- 页面关键结构缺失或解析器不兼容：结构错误；
- 任务 URL、城市或固定配置无效：配置错误；
- 暂无排片或暂时找不到目标影院：正常未开票，不视为程序错误。

连续 5 次结构错误或配置错误后，任务进入 `ERROR`，并创建一次系统告警。临时网络错误采用受限退避，但任何自动重试都不得快于 60 秒。成功检查后清零连续失败计数。

用户处理异常后可以手动恢复任务；恢复操作清零连续失败计数、清除旧领取租约，并把 `next_check_at` 设置为当前时间，使 Worker 立即重新检查。

任务到达目标日期的业务截止时间仍未开票时进入 `EXPIRED`，创建一次到期通知，不再检查猫眼。业务截止按 `Asia/Shanghai` 判断：只有本地日期已经晚于 `show_date` 才到期，因此目标观影日当天仍继续使用紧急间隔监控。

## 9. 通知与 Agent Mail

### 9.1 固定身份

本阶段固定：

- 发件人：`mijiatong@agent.qq.com`；
- 收件人：`850634546@qq.com`；
- Agent Mail workspace：`ticketwatch-server`。

不提供网页修改发件人、SMTP 或 Agent Mail 授权的功能。Worker 启动或发送前检查当前 Agent Mail 身份；实际邮箱不匹配时停止邮件发送并记录去敏错误。

### 9.2 服务器授权

Worker 镜像安装官方 `@tencent-qqmail/agently-cli`，版本在构建时固定并可控升级。设计确认时 npm 最新版为 `1.0.15`。

首次部署在 Worker 的实际 Linux 运行环境中执行 OAuth 设备登录：

```text
AGENTLY_WORKSPACE=ticketwatch-server agently-cli auth login
```

操作者在自己的浏览器完成授权。Agent Mail 配置目录和 Linux 凭据存储必须位于受保护的持久化卷中，不复制 Mac 钥匙串，也不把访问令牌写入 Git、Dockerfile、Compose 文件、数据库或日志。

由于 CLI 明确使用系统密钥库，部署实施必须先完成 Linux 容器预检：登录、身份查询、测试发送、Worker 容器重启、服务器服务重启后再次身份查询。只有凭据能跨重启有效保存，才允许启动真实任务。若目标容器环境无法提供可靠的系统密钥库，实施应暂停邮件切换并回到设计评审，不能用长期明文访问令牌绕过。

### 9.3 重试和幂等

邮件失败按 1、5、15、30、60 分钟重试。永久地址错误不重试。明确的认证或身份错误暂停邮件通道并显示在健康状态中。

`SENDING` 表示请求已经提交。进程在此状态崩溃且无法取得确定结果时，恢复流程把记录置为 `NEEDS_REVIEW`，不得自动盲目重发，以避免重复提醒。只有确定失败的通知才能按计划重试。

## 10. 私有访问与安全

### 10.1 SSH 隧道

用户在 Mac 执行：

```text
ssh -N -L 18000:127.0.0.1:8000 admin@47.116.69.108
```

浏览器访问：

```text
http://127.0.0.1:18000
```

SSH 断开只影响网页访问，不影响服务器 Worker。阿里云安全组只开放 `22/TCP`，且应在可行时限制 SSH 来源 IP。`80`、`443`、`8000`、`5432` 和 `6379` 均不开放公网。

### 10.2 应用安全

- Django 使用 `DEBUG=0`；
- Web 只发布宿主机 `127.0.0.1:8000`；
- PostgreSQL 和 Redis 只位于 Docker 内部网络；
- 静态文件由 WhiteNoise 随 Gunicorn 提供，不增加 Nginx；
- Django secret、数据库密码和其他密钥只来自 `/opt/ticketwatch/.env`；
- `.env` 权限为 `0600`，不加入 Git；
- 容器使用非 root 用户；
- 日志不得输出令牌、完整 Cookie、授权信息或原始敏感响应；
- 当前阶段不增加应用登录，因为 SSH 私有通道已经是访问边界。

## 11. 资源预算

针对 1.8 GiB 内存服务器采用以下约束：

- `web`：Gunicorn 单进程、少量线程；
- `worker`：单进程、并发 1；
- PostgreSQL：低 `max_connections`，小型共享缓存；
- Redis：约 64 MiB 内存上限，`noeviction`，只存短期协调数据；
- Docker 日志启用大小和文件数量限制；
- Compose 服务配置健康检查和 `restart: unless-stopped`；
- 不部署 Celery、Nginx、Certbot、OpenClaw 或 LLM 服务。

资源限制需要在真实服务器上观察，避免容器限制总和挤占操作系统和现有进程。Swap 是故障缓冲，不应成为稳定运行时的主要内存来源。

## 12. 备份、恢复和日志

### 12.1 备份

- 首次迁移前备份 SQLite；
- PostgreSQL 每日执行一次压缩逻辑备份；
- 服务器保留最近 7 天；
- 每次涉及数据库迁移的升级前额外备份；
- 每周至少复制一份到用户 Mac；
- `.env` 与 Agent Mail 凭据不混入普通数据库备份。

宿主机使用 systemd timer 或 cron 触发备份脚本，不新增常驻备份容器。备份写入临时文件成功后再原子改名，失败文件不得伪装成有效备份。

### 12.2 恢复演练

部署验收前必须在临时数据库中实际恢复最新备份，并核对：

- migration 状态；
- 各业务表数量；
- 活动任务及其 `next_check_at`；
- 已发送通知的唯一性；
- 页面能读取恢复后的数据。

### 12.3 日志和健康状态

必须能够查看：

- Web 健康状态；
- PostgreSQL 和 Redis 连通性；
- Worker 最近心跳；
- 最近一次猫眼成功检查；
- 监控中、异常、已开票和待发通知数量；
- Agent Mail 当前身份和授权状态；
- 数据库最近备份时间；
- 磁盘剩余空间。

Docker 日志设置轮转上限，避免填满 40 GB 系统盘。正常检查不保存完整猫眼 HTML；结构错误可保存经过大小限制和去敏处理的诊断摘要。

## 13. 部署、升级与回滚

### 13.1 首次部署

1. 备份当前 SQLite 和必要本机状态；
2. 在 Alibaba Cloud Linux 安装 Docker Compose 插件；
3. 在 `/opt/ticketwatch/app` 克隆并固定 Git 提交；
4. 创建受保护的服务器 `.env` 和数据目录；
5. 构建镜像并启动 PostgreSQL、Redis；
6. 执行 Django migration；
7. 导入并核对 SQLite 数据；
8. 启动 Web，先通过 SSH 隧道只读验证；
9. 在 Worker 环境完成 Agent Mail 授权及跨重启预检；
10. 启动 Worker；
11. 执行真实猫眼检查和真实测试邮件；
12. 配置每日备份、日志轮转和开机恢复；
13. 完成恢复演练与全部验收项目。

### 13.2 升级

1. 确认工作区干净并记录当前 Git 提交；
2. 生成升级前 PostgreSQL 备份；
3. 拉取并检出明确的新提交，不依赖模糊的 `latest`；
4. 构建新镜像；
5. 执行向后兼容的数据库迁移；
6. 依次检查 PostgreSQL、Redis、Web、Worker；
7. 验证 Agent Mail 身份、任务调度和页面。

破坏性 schema 变更采用“先增加、再切换、后删除”的多版本方式。一次部署中不得同时删除旧字段并使旧镜像无法启动。

### 13.3 回滚

应用问题优先回滚到上一 Git 提交和对应镜像。数据库迁移可兼容旧版本时不恢复数据库；只有发生数据破坏且明确确认目标备份后，才执行数据库恢复。任何数据库恢复前先保留当前故障现场备份。

## 14. 验收标准

本阶段完成必须同时满足：

1. Mac 通过 SSH 隧道能够打开 Web；
2. 公网不能直接连接 Django、PostgreSQL 或 Redis；
3. 可以创建、编辑、暂停、恢复和取消多条任务；
4. 三级检查间隔和两个时间边界可修改，间隔无法设置为 60 秒以下；
5. 多条任务按 `next_check_at` 独立执行；
6. 真实猫眼已有排片链路可以被正确识别；
7. `mijiatong@agent.qq.com` 能向 `850634546@qq.com` 发送真实提醒；
8. 同一开票事件只生成并成功发送一条开票通知；
9. Web 重启不停止 Worker；
10. Worker 重启后能重新领取到期任务；
11. 整台服务器重启后服务自动恢复；
12. Redis 清空或重启后永久业务数据不丢失；
13. 旧 SQLite 数据完整迁入 PostgreSQL；
14. PostgreSQL 备份能在临时数据库实际恢复；
15. 日志中不存在 OAuth 令牌、数据库密码或完整敏感 Cookie；
16. 服务器在连续运行观察期内无持续 Swap 抖动、OOM 或磁盘异常增长。

## 15. 后续阶段入口

完成并稳定运行本阶段后，后续设计可以依次讨论：

1. 域名、ICP 备案、HTTPS 和公网登录；
2. 多用户、权限隔离和用户级通知配置；
3. 用户 SMTP 或其他邮件通道；
4. OpenClaw 与 LLM 自然语言入口；
5. 电影、影院自动发现和推荐；
6. 大麦等其他平台适配。

这些能力不得提前混入当前部署，以免在 2 GB 服务器上引入未经验证的资源和安全负担。
