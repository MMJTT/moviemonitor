# 猫眼本地单任务监控 MVP 设计规格

日期：2026-08-16
状态：交互设计已确认，待书面规格确认

## 1. 目标

构建一个只在用户本机运行的网页应用。用户通过浏览器配置自己的 SMTP 邮箱，创建一个“城市 + 电影 + 日期 + 影院”猫眼开票监控任务。当目标影院首次出现有效“选座购票”入口时，应用发送一封开票邮件；日期结束仍未开票时，发送一封到期邮件。

MVP 的成功标准是完成以下本地闭环：

1. 一条命令启动网页和后台监控；
2. 网页配置并测试 SMTP；
3. 网页预览猫眼 URL，选择或手动输入一家影院；
4. 创建任务后立即检查，此后按可配置间隔监控；
5. 开票或到期时只发送一次对应邮件；
6. 退出后重新启动，任务和通知状态从 SQLite 恢复。

## 2. MVP 范围

### 2.1 包含

- 本机回环地址上的中文网页；
- 无登录的单用户模式；
- SQLite 持久化；
- 一个 SMTP 配置，授权码加密保存；
- 同一时间最多一个未结束任务；
- 每个任务只监控一家影院；
- 城市独立选择；
- 猫眼影院筛选 URL 校验和预览；
- 从当前可见影院中选择一家；
- 影院尚未出现时手动输入完整名称；
- 创建后立即检查；
- 一个可修改的固定轮询间隔，最低 60 秒；
- 精确影院匹配和一次性开票邮件；
- 日期结束后一次性到期邮件；
- 暂停、恢复、取消和查看最近检查记录；
- 进程重启后的 SQLite 状态恢复。

### 2.2 不包含

- 多用户、登录、邀请、角色或管理员后台；
- 同时监控多个任务、电影或影院；
- PostgreSQL、Redis、Celery 或 Docker；
- 阿里云、公网访问、Nginx、HTTPS 或证书；
- 服务器备份和运维监控；
- 自动选座、下单、付款或验证码绕过；
- 票价、场次、影厅、座位和余票解析；
- 大麦或其他平台适配；
- 开票完成后的新增场次和回流票提醒。

## 3. 运行方式

使用 Python 3.12、Django、SQLite、Requests、Beautiful Soup 和 cryptography/Fernet。

用户运行：

```bash
python manage.py runlocal
```

`runlocal` 在同一 Python 进程内：

- 启动一个后台监控线程；
- 以关闭自动重载的方式启动 Django 本地开发服务器；
- 仅监听 `127.0.0.1:8000`；
- 确保调度器只启动一次；
- 在进程退出时停止调度循环。

浏览器关闭不影响监控，终端中的 `runlocal` 进程退出后监控停止。再次启动时，调度器从 SQLite 中读取未结束任务和 `next_check_at` 后继续。

## 4. 组件边界

### 4.1 Web 层

负责表单、页面、CSRF、防止重复提交和用户操作。Web 层不直接解析猫眼 HTML、不直接实现 SMTP 协议，也不持有调度状态。

页面包括：

- `/`：任务仪表盘；
- `/smtp/`：SMTP 配置与测试邮件；
- `/task/new/`：城市和猫眼 URL 预览、影院选择或手动输入；
- `/task/<id>/`：任务详情与最近检查/通知记录；
- `/task/<id>/pause|resume|cancel/`：仅接受 POST；
- `/settings/`：固定轮询间隔设置。

### 4.2 猫眼适配器

负责：

- 验证并规范化目标 URL；
- 使用独立选择的城市 `ci` Cookie 请求页面；
- 识别有效列表、有效空列表、验证码、限流和结构异常；
- 返回统一的电影、日期、影院 ID、影院名称、开票状态和购票链接。

网页、调度器和通知逻辑只依赖适配器返回值，不直接依赖 CSS 选择器。

### 4.3 监控服务

负责任务创建、状态转换、精确影院匹配、检查记录、下一次检查时间和通知幂等。网络请求和 SMTP 发送期间不持有 SQLite 写事务。

### 4.4 本地调度器

后台线程使用进程锁保证同一时刻只有一个检查。调度器周期性读取 SQLite 中到期的唯一活动任务；SQLite 中的 `next_check_at` 是调度事实来源，线程内存不是事实来源。

### 4.5 邮件服务

负责 SMTP SSL 或 STARTTLS 连接、测试邮件、开票邮件、到期邮件和错误分类。邮件服务不记录授权码或完整邮件正文。

## 5. 数据模型

### 5.1 `SMTPConfig`

单例记录：

- SMTP 主机和端口；
- 安全模式：SSL 或 STARTTLS；
- 用户名、发件地址和收件地址；
- Fernet 加密后的授权码；
- 是否测试成功、最近测试时间和去敏错误摘要；
- 创建和更新时间。

任务启动前必须存在测试成功的 SMTP 配置。

### 5.2 `AppSetting`

单例记录：

- `poll_interval_seconds`，默认 60；
- 模型和表单均校验不低于 60；
- 更新时间。

修改后，下一次成功检查在计算 `next_check_at` 时使用新值。

### 5.3 `MonitorTask`

- UUID；
- 原始 URL 和规范化 URL；
- 城市名称和猫眼 `ci`；
- `movieId`、电影名称和 `showDate`；
- 目标影院显示名称、规范化名称和可空影院 ID；
- 购票链接；
- 状态；
- 连续失败次数、最近去敏错误；
- 上次检查、下次检查、检测开票、通知成功、完成、过期和取消时间；
- 创建和更新时间。

状态包括：

- `MONITORING`：等待开票；
- `PAUSED`：用户暂停；
- `DETECTED`：已检测到开票，邮件尚未成功；
- `COMPLETED`：开票邮件已成功；
- `EXPIRED`：日期结束且未完成；
- `CANCELLED`：用户取消；
- `ERROR`：连续结构或平台异常，需要用户处理后恢复。

数据库条件唯一约束保证同一时间最多一个 `MONITORING`、`PAUSED`、`DETECTED` 或 `ERROR` 任务。

### 5.4 `CheckRun`

- 所属任务；
- 开始和结束时间；
- 状态：成功、临时错误、限流、结构错误或配置错误；
- HTTP 状态和响应内容指纹；
- 找到的影院数量；
- 去敏错误代码和摘要。

不默认保存完整猫眼响应。

### 5.5 `Notification`

- 所属任务；
- 类型：`OPENING` 或 `EXPIRY`；
- 状态：待发送、发送中、成功、失败或永久失败；
- 重试次数、下次重试时间；
- 固定 Message-ID；
- 去敏 SMTP 响应和错误摘要；
- 创建、发送和更新时间。

数据库唯一约束 `(task, type)` 防止重复创建同类通知。

## 6. 创建任务流程

1. 检查 SMTP 已测试成功。
2. 用户选择城市并粘贴猫眼 URL。
3. 服务端只允许 HTTPS、`maoyan.com`/`www.maoyan.com` 和 `/cinemas`，拒绝用户信息、非标准端口、片段、重复关键参数和重定向。
4. URL 必须包含一个数字 `movieId` 和一个 ISO `showDate`，日期不能早于本地当天。
5. 服务端使用城市 `ci` Cookie 请求页面并验证城市、电影和日期。
6. 预览页展示电影、日期和当前可见影院。
7. 用户选择一个影院，或手动输入一个完整影院名称。
8. 预览结果使用带时效的服务端签名；确认操作不信任浏览器重新提交的电影、日期、城市或影院元数据。
9. 创建任务后立即检查。
10. 若已开票，进入与正常轮询相同的幂等通知路径。

## 7. 开票判定

影院名称只为匹配而规范化：Unicode NFKC、大小写折叠、中英文括号统一、首尾空白删除和连续空白合并。展示名称保持原样。

判定开票必须同时满足：

- 响应是有效的猫眼影院列表页面；
- 页面城市、`movieId` 和 `showDate` 与任务一致；
- 在独立 `.cinema-cell` 中找到目标影院；
- 已知影院 ID 时按 ID 匹配；
- 手动影院尚无 ID 时要求规范化后的完整名称精确相等，首次成功后保存 ID；
- 影院卡片内存在有效的猫眼“选座购票”链接。

筛选区、页头、脚本或其他无关位置出现影院名称不算开票。近似名称、子串和同品牌其他门店不算开票。

## 8. 调度、失败与恢复

- 创建任务后立即检查一次；
- 正常检查间隔来自 `AppSetting`，默认 60 秒且不可低于 60 秒；
- 用户修改间隔后，下一次调度计算立即使用新值；
- 网络错误或 HTTP 5xx 按 2、5、15、30、60 分钟退避，实际等待时间取配置间隔和退避值中的较大者；
- HTTP 403/429 或验证码按平台异常处理，不视为未开票；
- HTTP 200 但缺少关键结构按结构错误处理，不视为未开票；
- 连续五次平台或结构异常将任务置为 `ERROR`，停止自动检查；用户确认页面恢复后可手动恢复；
- 一次有效检查重置连续失败次数；
- 每次调度先持有进程检查锁，再重新读取并锁定短事务内的任务状态，避免暂停/取消后仍继续写入结果；
- 进程重启后从 SQLite 的 `next_check_at`、任务状态和通知状态恢复；
- 对崩溃时处于 `SENDING` 的邮件不自动重复发送，网页提示其结果不确定，避免 SMTP 已接受后再次发送。

## 9. 通知规则

### 9.1 开票邮件

只发送一次，包含：电影、日期、城市、影院、检测时间、原始监控 URL 和购票链接。不包含票价、场次、影厅、座位或余票。

SMTP 成功接受后，通知变为成功，任务变为 `COMPLETED`。临时邮件错误只重试邮件，不重新请求猫眼；认证或收件人永久错误停止自动重试并在网页提示。

临时邮件错误按 1、5、15、30、60 分钟重试，最多安排五次重试。每次重试时间写入 SQLite；本地调度器扫描到期的待发送通知，因此重启进程不会依赖内存计时器恢复。

### 9.2 到期邮件

Asia/Shanghai 时区中，当 `showDate < localdate()` 且任务未完成时：

- 停止轮询；
- 任务变为 `EXPIRED`；
- 创建并发送一封到期邮件；
- 数据库唯一约束保证只创建一次。

## 10. 本地安全

- 服务只监听 `127.0.0.1`，不提供局域网或公网入口；
- 保留 Django CSRF、中间件和安全表单处理；
- SMTP 授权码使用 Fernet 认证加密；
- 首次保存 SMTP 前自动生成 `.ticketwatch.key`，使用受限文件权限并加入 `.gitignore`；
- 如果数据库已有密文但密钥丢失，应用拒绝解密并要求重新输入授权码，不静默生成新密钥覆盖错误；
- 授权码字段每次打开均为空，留空表示保留现有密文；
- 日志不得包含授权码、Cookie、完整邮件正文或完整异常服务器响应；
- 猫眼 URL 使用协议、主机、端口、路径、参数和重定向白名单防止 SSRF。

## 11. 测试策略

严格使用测试先行实现业务行为。自动测试覆盖：

- URL 规范化和 SSRF 拒绝；
- 城市 Cookie；
- 有效开票、有效空列表、验证码和结构缺失固定 HTML；
- 影院 ID 优先和手动名称精确匹配；
- SMTP 授权码加解密与不回显；
- SMTP 测试成功/失败；
- 单一活动任务约束；
- 创建时立即开票；
- 轮询最低 60 秒和修改后生效；
- 检查重入锁；
- 开票通知幂等、临时重试和永久失败；
- Asia/Shanghai 到期边界和到期通知幂等；
- 暂停、恢复、取消；
- 进程重启后的任务和待发通知恢复；
- 页面只允许本地单用户流程且状态修改使用 POST + CSRF。

猫眼解析测试仅使用去敏、最小固定 HTML，不依赖实时网站。真实猫眼和真实 SMTP 只用于用户主动执行的预览、测试邮件和本地验收。

## 12. 验收标准

MVP 完成必须同时满足：

1. `python manage.py runlocal` 一条命令启动本地网页和唯一监控线程。
2. 服务只监听 `127.0.0.1:8000`，浏览器关闭后监控继续。
3. SMTP 授权码加密保存且不回显，测试邮件能够成功发送。
4. 用户能选择城市、粘贴猫眼 URL，并选择或手动输入一家影院。
5. 同一时间不能创建第二个未结束任务。
6. 创建时已开票会立即进入一次性邮件路径。
7. 有效空列表不会通知；验证码、限流和结构异常不会误报。
8. 固定间隔可修改但不能低于 60 秒，修改后下一轮生效。
9. 每个任务最多一封开票邮件和一封到期邮件。
10. 开票邮件成功后任务完成并停止检查。
11. 日期结束未完成时任务过期并发送一次到期邮件。
12. 暂停、恢复、取消和最近检查/错误可在网页操作或查看。
13. 停止并重新运行进程后，SQLite 中的任务、检查和通知事实不会丢失或重复创建。
