# 多用户票务开票监控平台设计规格

日期：2026-08-16
状态：已完成交互确认，待用户审阅书面规格
第一阶段平台：猫眼电影

## 1. 目标

构建一个部署在阿里云 Linux 服务器上的多用户网页系统。用户通过管理员邀请激活账号，配置自己的 SMTP 邮箱，创建猫眼电影开票监控任务。

每个任务由以下条件组成：

- 城市；
- 猫眼影院筛选 URL；
- URL 中指定的电影；
- URL 中指定的观影日期；
- 一家或多家目标影院。

当“指定城市 + 指定电影 + 指定日期 + 指定影院”首次出现有效的“选座购票”入口时，系统向任务所有者发送邮件。每家目标影院独立通知一次；全部影院通知成功后，任务自动完成。

## 2. 范围

### 2.1 第一阶段包含

- 邀请制多用户账号；
- 用户自有 SMTP 配置；
- 猫眼 URL 解析和验证；
- 城市独立选择；
- 页面已有影院勾选；
- 尚未开票时手动预填影院名称；
- 单影院和多影院任务；
- 自适应轮询、查询合并、抖动和失败退避；
- 每家影院一次性开票邮件；
- 到期未开票邮件；
- 管理员管理、日志、暂停和故障查看；
- Docker Compose 部署；
- 公网 IP HTTPS 证书和自动续期；
- PostgreSQL 备份与恢复流程。

### 2.2 第一阶段不包含

- 自动选座、自动下单或自动付款；
- 抢票、验证码绕过、登录绕过或风控规避；
- 票价解析和价格提醒；
- 具体场次、影厅、座位或余票数量解析；
- 开票后新增场次和回流票的持续提醒；
- 公开注册；
- 大麦等其他平台的实际适配。

## 3. 已验证的猫眼行为

技术验证使用了以下形式的页面：

`https://www.maoyan.com/cinemas?brandId=<brand>&movieId=<movie>&showDate=<YYYY-MM-DD>`

验证结果：

- `movieId` 和 `showDate` 会参与影院列表筛选；
- 城市不可靠地包含在 URL 中，由 Cookie `ci` 控制，因此创建任务时必须另选城市；
- 已开票时，目标影院出现在 `.cinema-cell` 中，并包含影院名称和有效“选座购票”链接；
- 尚未开票时，可能出现 `.no-cinemas`，且没有对应影院卡片；
- 页面票价使用动态字体混淆，但本系统不解析票价，因此不影响核心目标；
- 普通 HTTP 请求能够获得所需服务端 HTML，第一阶段不需要 Selenium；
- 页面返回 HTTP 200 不代表业务页面有效，仍需校验关键结构并识别验证码或反爬页面。

## 4. 技术方案

采用 Django 模块化单体：

- Django：网页、用户认证、权限、管理员功能和业务接口；
- Django 模板 + Bootstrap：中文网页界面；
- PostgreSQL：永久业务数据；
- Celery：后台检查、邮件发送和失败重试；
- Redis：Celery broker 和短期任务协调，不作为永久状态来源；
- Celery Beat：周期性扫描到期任务并创建合并检查；
- Nginx：HTTPS 终止、反向代理和静态文件；
- Certbot：公网 IP 短期证书申请和自动续期；
- Docker Compose：开发外的统一部署方式。

系统采用平台适配器边界。Django 的用户、任务、调度和通知模块只依赖统一结果模型，不直接依赖猫眼 HTML。第一阶段实现 `MaoyanAdapter`，后续可新增 `DamaiAdapter`。

Docker Compose 服务：

| 服务 | 职责 | 是否暴露公网 |
|---|---|---|
| `nginx` | HTTPS、反向代理、静态文件、ACME 验证 | 80/443 |
| `web` | Django Web 应用 | 否 |
| `worker-check` | 猫眼检查任务 | 否 |
| `worker-mail` | SMTP 邮件与重试 | 否 |
| `beat` | 到期任务调度 | 否 |
| `postgres` | 永久数据 | 否 |

PostgreSQL、Redis、应用容器只加入内部 Docker 网络，不发布 5432、6379 或 Django 内部端口。公网安全组只保留管理所需的 SSH、HTTP 和 HTTPS；SSH 来源范围在部署时尽量收紧。

## 6. 核心数据模型

### 6.1 用户 `User`

- 邮箱；
- 密码哈希；
- 角色：管理员或普通用户；
- 状态：待激活、启用、停用；
- 最近登录时间；
- 创建和更新时间。

### 6.2 邀请 `Invitation`

- 一次性随机令牌的哈希；
- 目标邮箱；
- 创建管理员；
- 过期时间；
- 使用时间；
- 状态。

公开注册关闭。管理员创建用户或生成一次性邀请链接。

### 6.3 SMTP 配置 `SMTPConfig`

- 所属用户，一对一；
- SMTP 主机、端口；
- 安全模式：SSL/TLS 或 STARTTLS；
- 用户名和发件地址；
- 加密后的授权码；
- 最近测试状态和时间；
- 最后错误摘要。

授权码使用成熟加密库提供的认证加密保存。加密主密钥仅从服务器环境变量读取，不写入数据库、镜像、代码仓库或日志。任务启用前要求 SMTP 测试成功。

### 6.4 监控任务 `MonitorTask`

- 所属用户；
- 平台，第一阶段固定为 `maoyan`；
- 用户输入的原始 URL；
- 规范化 URL；
- 城市名称和猫眼 `ci`；
- `movieId`、电影名称；
- `showDate`；
- `brandId` 等保留筛选参数；
- 状态；
- 下次检查时间；
- 当前基础检查间隔；
- 连续失败次数；
- 最近成功和失败时间；
- 到期时间；
- 创建、启动、完成、暂停和取消时间。

### 6.5 目标影院 `TaskCinema`

- 所属任务；
- 用户输入或页面解析得到的原始影院名称；
- 规范化影院名称；
- 猫眼影院 ID，未解析时可为空；
- 当前状态；
- 首次检测开票时间；
- 邮件发送成功时间；
- 猫眼购票链接；
- 最后匹配说明。

同一任务内影院名称或影院 ID 不允许重复。

### 6.6 检查记录 `CheckRun`

- 合并查询键；
- 开始和结束时间；
- HTTP 与解析状态；
- 响应摘要和内容指纹，不默认保存完整页面；
- 找到的影院数量；
- 关联任务数量；
- 错误类别和去敏错误摘要。

正常成功记录保留精简信息，错误记录保留更长时间。日志保留周期作为系统设置提供，默认成功记录 30 天、错误记录 90 天。

### 6.7 通知记录 `Notification`

- 用户、任务和目标影院；
- 通知类型：开票、任务过期、系统告警；
- 状态：待发送、发送中、成功、失败、永久失败；
- 重试次数和下次重试时间；
- SMTP 响应摘要；
- Message-ID；
- 创建、发送和失败时间。

### 6.8 审计日志 `AuditLog`

记录登录、邀请、用户停用、SMTP 配置变更、任务操作、管理员全局暂停和平台适配器暂停。审计内容不得包含密码、授权码、完整 Cookie 或其他凭据。

## 7. 状态机

### 7.1 任务状态

主路径：

`草稿 → 监控中 → 部分开票 → 已完成`

其他状态：

- `已暂停`：用户或管理员暂停，可恢复；
- `异常`：连续检查异常达到阈值，需要处理；
- `已过期`：观影日期结束仍有影院未通知；
- `已取消`：用户主动终止，不可自动恢复。

### 7.2 影院状态

`等待开票 → 已检测到开票 → 邮件发送中 → 已通知`

发送失败时进入可重试的 `通知失败`，但保留“已检测到开票”的事实。只有邮件发送成功后才进入 `已通知`。所有目标影院均为 `已通知` 后，任务自动进入 `已完成` 并停止检查。

## 8. 创建任务流程

1. 用户登录并确保 SMTP 已测试成功。
2. 用户选择城市。
3. 用户粘贴猫眼影院筛选 URL。
4. 服务端要求主机属于猫眼允许列表，路径属于影院列表，并解析 `movieId`、`showDate` 和保留筛选参数。
5. 服务端使用城市 `ci` Cookie 请求页面，验证页面声明的查询日期和 URL 一致。
6. 系统展示解析到的电影、日期和当前影院列表。
7. 用户勾选当前存在的影院；若影院尚未出现，可手动输入完整名称。
8. 系统展示最终条件，用户确认启动。
9. 系统立即执行首次检查。
10. 如果目标影院已经开票，立即创建邮件通知；邮件成功后记录该影院已通知。

URL 校验必须防止 SSRF：服务端不请求用户提供的任意主机、IP、重定向目标或协议。重定向后的最终主机也必须重新校验。

## 9. 影院匹配和开票判定

### 9.1 影院名称规范化

规范化操作只用于匹配，不修改展示名称：

- Unicode 规范化；
- 去除首尾空白并合并连续空白；
- 英文字母不区分大小写；
- 中文和英文括号统一；
- 常见分隔空格统一。

不使用宽泛的任意子串命中作为最终开票条件，避免同名或近似名称误报。

### 9.2 ID 优先

影院首次通过页面卡片匹配成功后保存猫眼影院 ID。以后优先按 ID 匹配，名称作为一致性校验。手动输入且页面尚无影院时，ID 为空；第一次精确名称匹配成功后补全 ID。

### 9.3 开票条件

同时满足以下条件才判定开票：

- 响应是有效猫眼影院列表页面；
- 页面城市和任务城市一致；
- 页面查询的 `movieId` 和 `showDate` 与任务一致；
- 找到目标影院的独立影院卡片；
- 卡片包含有效的猫眼影院或选座购票链接；
- 链接关联的影院 ID 与已知 ID 一致，或首次精确名称匹配成功。

只在筛选区、脚本数据、页头或其他无关位置出现影院名称，不算开票。

## 10. 调度与查询合并

Celery Beat 每 30 秒扫描一次到期任务，但任何业务任务的有效检查间隔不得小于 60 秒。

默认自适应基础间隔：

- 距观影日期超过 7 天：15 分钟；
- 距观影日期 2 至 7 天：5 分钟；
- 距观影日期不足 48 小时，包括观影当天：1 分钟。

每次计划加入随机正向抖动，保证实际间隔不低于 60 秒。用户不能配置更低间隔。

查询合并键至少包含：

- 平台；
- 城市 `ci`；
- `movieId`；
- `showDate`；
- 影响影院列表的规范化筛选参数。

相同合并键在同一时间窗口只产生一次平台请求，结果分发给所有关联任务和影院。

使用 Redis 分布式锁和数据库幂等约束防止多个 worker 重复检查或重复通知。PostgreSQL 是任务和通知事实的最终来源。

## 11. 失败退避和异常语义

- 网络超时、连接失败、HTTP 5xx：不改变开票状态，按 2、5、15、30 分钟逐步退避；成功后恢复自适应间隔。
- HTTP 403、429、验证码或明确反爬页面：标记平台检查异常并延长间隔；达到阈值后暂停猫眼适配器或相关查询组。
- HTTP 200 但缺少关键页面结构：解析异常，不得视为未开票。
- 页面城市、电影或日期与任务不一致：配置或会话异常，不得触发通知。
- SMTP 临时错误：邮件队列独立重试，不重新请求猫眼。
- SMTP 永久认证错误：停止该用户的新邮件发送，在网页中提示重新测试 SMTP；已检测到的开票事实不得丢失。
- 应用或 worker 重启：依靠 PostgreSQL 状态恢复，不能因内存状态丢失重复发送。

连续失败阈值和退避上限可由管理员配置，默认连续 5 次异常将任务或查询组标记为 `异常`。

## 12. 通知规则

### 12.1 开票邮件

每家影院首次开票发送一封。内容包含：

- 电影名称；
- 指定日期；
- 城市；
- 影院名称；
- 检测时间，时区为 Asia/Shanghai；
- 原始监控 URL；
- 目标影院卡片提供的猫眼购票链接。

不包含解析票价、场次、影厅或座位信息。

### 12.2 任务过期邮件

任务到期时间为指定日期在 Asia/Shanghai 时区的当天结束。仍有未通知影院时：

- 任务进入 `已过期`；
- 停止轮询；
- 发送一封任务结束邮件，列出未检测到开票的影院；
- 邮件发送失败按独立邮件重试策略处理。

### 12.3 幂等

数据库为“任务 + 目标影院 + 通知类型”建立唯一幂等约束。并发 worker、任务重试或应用重启不能产生重复开票邮件。

## 14. 安全设计

- Django 使用 Argon2 等强密码哈希；
- 全站 HTTPS，安全会话 Cookie、HttpOnly、SameSite 和 CSRF 防护；
- 登录和邀请激活接口限速；
- 公开注册关闭；
- 邀请令牌只保存哈希并设置过期时间；
- 所有业务查询都按当前用户过滤，管理员能力显式授权；
- SMTP 授权码应用层认证加密；
- 日志过滤密码、授权码、Cookie、会话、邀请令牌和完整邮件凭据；
- 猫眼 URL 使用主机、协议、端口、路径和重定向白名单，防止 SSRF；
- Django 管理后台不直接作为公网普通入口，管理员仍需强认证；
- 容器以非 root 用户运行，镜像和依赖在实施阶段进行漏洞检查；
- 数据库备份加密并限制读取权限。

## 15. HTTPS IP 证书

使用 Let’s Encrypt 公网 IP 短期证书：

- 证书绑定 `47.116.69.108`；
- 使用支持 IP 证书和 short-lived profile 的 Certbot 5.4 或更高版本；
- 使用 HTTP-01/webroot 或兼容方案完成校验；
- 证书有效期约 6 天，必须配置频繁自动续期；
- 续期成功后通过 deploy hook 安全重载 Nginx；
- 续期失败进入系统告警，并在证书到期前重复提醒管理员。

参考：

- https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability.html
- https://letsencrypt.org/2026/03/11/shorter-certs-certbot.html

## 16. 备份、日志和健康检查

- PostgreSQL 数据目录使用持久化卷；
- 每日执行逻辑备份，默认保留 7 份日备份和 4 份周备份；
- 定期执行恢复演练，只有可恢复的备份才算有效；
- Redis 不保存唯一业务事实，可在必要时重建；
- 证书、Nginx 配置和应用日志使用独立持久化卷；
- 日志按天或大小轮转；
- 每个容器提供健康检查和合理重启策略；
- 监控指标至少覆盖 Web 健康、队列积压、到期任务延迟、猫眼错误率、解析错误率、SMTP 失败率、数据库备份和证书剩余时间。

- 邮件失败后恢复；
- 任务到期邮件；
- 查询合并和并发幂等；
- worker 或 Redis 重启后的状态恢复。

### 17.4 部署验收

- 公网 IP HTTPS 无浏览器证书警告；
- HTTP 自动跳转 HTTPS；
- PostgreSQL、Redis 和应用内部端口不暴露公网；
- 容器重启后任务继续；
- 证书自动续期及 Nginx 重载演练通过；
- PostgreSQL 备份恢复演练通过；
- 管理员邀请用户、用户配置 SMTP、创建任务和收到测试邮件的完整流程通过。

## 18. 平台扩展边界

统一平台适配器至少提供：

- 验证并规范化用户目标；
- 发现当前可见影院；
- 检查目标影院可购状态；
- 返回统一电影、日期、影院 ID、影院名称、状态和购票链接；
- 识别平台限流、验证码、页面变化和不可重试配置错误。

大麦适配不进入第一阶段。未来新增大麦时，沿用现有用户、任务、调度、通知、日志和后台管理，只实现新的平台适配器及其配置字段。

## 19. 参考项目及采用边界

- `aviiciii/bms-ticket-notifier`：参考“保存上次状态并比较新日期/新场次”的状态模型；不复用其平台接口。
- `jacket-sikaha/maoyan-service`：参考影院级采集、调度、通知日志和去重；通知条件改为指定日期首次开票。
- `xhconceit/MaoYanApi`：参考猫眼 `movieId`、`showDate`、影院和城市参数语义；旧接口必须重新验证，不直接依赖。
- `ThinkerWen/TicketMonitoring`：只参考多平台适配器组织思路；其演唱会回流票逻辑不进入本项目。

## 20. 验收标准

第一阶段完成必须同时满足：

1. 管理员可以邀请用户，公开注册不可用。
2. 用户只能访问自己的数据。
3. 用户可以保存并测试自己的 SMTP 配置，授权码不会明文存储或回显。
4. 用户可以选择城市、粘贴猫眼 URL、选择或输入一家/多家影院并启动任务。
5. 系统能区分有效已开票页面、未开票页面和异常页面。
6. 每家影院首次开票只发送一封邮件；发送失败可恢复且不丢失开票状态。
7. 创建任务时已经开票会立即通知。
8. 多影院任务在全部影院通知成功后自动完成。
9. 日期结束仍未全部开票会停止任务并发送过期邮件。
10. 实际检查间隔永不低于 60 秒，相同查询得到合并。
11. 重启 Web、worker 或 Redis 不导致任务丢失或重复通知。
12. 公网仅通过受信任 HTTPS 访问，PostgreSQL 和 Redis 不暴露公网。
13. 证书自动续期和数据库备份恢复均通过演练。
14. 猫眼解析连续异常时不会产生误报，并能在管理页面被发现和暂停。
